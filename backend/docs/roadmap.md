РОАДМАП БЕКЕНДА ДЛЯ MVP

Стек: C#, ASP.NET Core, PostgreSQL, Entity Framework Core с Npgsql, облачная LLM через API.

Делаем одно серверное приложение и одну активную игру. Сначала собираем рабочий сценарий с тестовыми ответами NPC, затем подключаем модель.

1. СОЗДАТЬ ОСНОВУ ПРОЕКТА

Задачи:
[ ] Создать ASP.NET Core-проект.
[ ] Подключить PostgreSQL через EF Core и Npgsql.
[ ] Настроить миграции.
[ ] Вынести строку подключения, адрес LLM API, название модели и API-ключ в настройки окружения.
[ ] Добавить проверку работоспособности сервера и подключения к БД.

Готово, когда: сервер запускается, подключается к PostgreSQL и создаёт таблицы.

2. СОЗДАТЬ МОДЕЛЬ ДАННЫХ

Минимальные сущности:

GameSession:
— ID и код комнаты;
— состояние игры;
— номер текущего раунда;
— ID ведущего.

Player:
— ID;
— ID сессии;
— имя;
— цвет.

Npc:
— ID сессии;
— номер от 1 до 10;
— имя и цвет;
— роль;
— номер настоящего друга или цель актёра;
— описание личности и доступная история в JSON.

Message:
— ID сессии;
— автор или NPC;
— текст;
— эмоция;
— время создания.

PairChoice:
— ID игрока;
— ID сессии;
— номер раунда;
— номера двух выбранных NPC.

[ ] Создать сущности и миграцию.
[ ] Добавить уникальность номера NPC внутри сессии.
[ ] Добавить уникальность выбора игрока внутри раунда.

Готово, когда: данные можно записать в БД и прочитать обратно.

3. СДЕЛАТЬ СОЗДАНИЕ ИГРЫ И ВХОД

[ ] Создание комнаты с назначением ведущего.
[ ] Вход по имени и коду комнаты.
[ ] Назначение игроку цвета.
[ ] Выдача простого токена для доступа к своей сессии.
[ ] Получение текущего состояния игры.
[ ] Проверка, что действия выполняются от имени авторизованного игрока.
[ ] Управление игрой доступно только ведущему.

Полноценные аккаунты и регистрацию не делаем.

Готово, когда: несколько игроков могут войти в одну комнату и получить её публичное состояние.

4. ПОДГОТОВИТЬ ДЕСЯТЬ NPC

[ ] Создать десять базовых описаний персонажей.
[ ] При создании партии случайно назначать три пары и четырёх актёров.
[ ] Настоящим друзьям выдавать общую историю.
[ ] Актёрам выдавать цель и собственную легенду.
[ ] Сохранять назначенные роли и истории в БД.
[ ] Сделать отдельные публичные данные NPC: номер, имя, цвет.
[ ] Исключить секретные роли и истории из обычных ответов клиенту.

Для экономии времени истории берём из подготовленных шаблонов. Не тратим запросы модели на генерацию всей партии.

Готово, когда: сервер знает правильные связи, а клиент получает только публичные сведения.

5. СОБРАТЬ ВОПРОСЫ С ТЕСТОВЫМИ ОТВЕТАМИ

[ ] Принимать номер NPC и текст вопроса.
[ ] Проверять номер, непустой текст и допустимую длину.
[ ] Проверять, разрешены ли вопросы сейчас.
[ ] Сохранять вопрос.
[ ] Возвращать временный тестовый ответ выбранного NPC.
[ ] Сохранять ответ в общей истории.
[ ] Возвращать понятную ошибку при некорректном запросе.

Готово, когда: фронтенд может выбрать NPC по номеру, отправить вопрос и показать ответ без подключения LLM.

6. ПОДКЛЮЧИТЬ ОБЛАЧНУЮ LLM

[ ] Создать отдельный LlmClient через HttpClient.
[ ] Настроить адрес API, модель и ключ.
[ ] Формировать контекст из личности NPC, доступных ему фактов и короткой истории разговора.
[ ] Настоящим друзьям передавать общую историю, актёрам — только их легенду и публично известные сведения.
[ ] Получать ответ с полями text и emotion.
[ ] Ограничить длину ответа и размер истории в запросе.
[ ] Проверять ответ перед сохранением.
[ ] При неизвестной эмоции использовать neutral.
[ ] При ошибке API возвращать сообщение о неудачном запросе и снимать состояние ожидания.

Для экономии лимитов:
— один запрос модели на один ответ NPC;
— без генерации реакций остальных девяти участников;
— без потоковой выдачи;
— без автоматических повторных запросов;
— вопросы обрабатываются по одной простой очереди.

Готово, когда: NPC отвечает с учётом своей роли и предыдущих реплик, а ответ сохраняется в PostgreSQL.

7. СДЕЛАТЬ УПРАВЛЕНИЕ ИГРОЙ И ВЫБОР ПАРЫ

[ ] Добавить состояния Lobby, Playing, PairSelection, Finished.
[ ] Ведущий может начать игру, открыть выбор пары, перейти дальше и завершить игру.
[ ] Принимать два номера NPC от игрока.
[ ] Запретить выбор одного NPC дважды в одной паре.
[ ] Принимать выбор только в состоянии PairSelection.
[ ] Сохранять одну пару на игрока за текущий раунд.
[ ] Повторное подтверждение до закрытия выбора обновляет существующую запись.
[ ] Чужие выборы до завершения игры не выдавать.
[ ] После завершения отдавать настоящие пары и роли NPC.

Автоматические таймеры не нужны: переходами управляет ведущий.

Готово, когда: игрок выбирает пару, сервер сохраняет её, а ведущий может продолжить игру.

8. ДОБАВИТЬ МИНИМАЛЬНУЮ ЛОГИКУ КРЕСЕЛ

[ ] Задать фиксированный список кресел игроков.
[ ] Хранить занятость кресел в памяти сервера.
[ ] Обрабатывать запросы сесть и встать.
[ ] Не разрешать двум игрокам одновременно занимать одно кресло.
[ ] Возвращать ID занятого кресла или состояние «стоит».

Для этой версии отдельная таблица кресел не требуется.

Готово, когда: сервер однозначно определяет, кто какое кресло занимает.

9. ПРОВЕРИТЬ ПОЛНЫЙ СЦЕНАРИЙ

[ ] Создать комнату и войти несколькими игроками.
[ ] Проверить состав NPC: три пары и четыре актёра.
[ ] Задать вопросы разным NPC.
[ ] Убедиться, что история разговора учитывается.
[ ] Сохранить выбор каждого игрока.
[ ] Перейти дальше и повторить выбор.
[ ] Завершить игру и раскрыть роли.
[ ] Проверить, что секретные данные не выдаются раньше времени.
[ ] Проверить ошибку облачного API и одновременную посадку на одно кресло.

ПОРЯДОК РАБОТЫ

Основа проекта → БД → комната и вход → NPC → тестовые вопросы → LLM → выбор пары и завершение → кресла → общая проверка.

Первый результат для передачи фронтенду: вход в комнату, список десяти NPC и тестовый ответ на вопрос. Это позволит собирать интерфейс, пока подключается облачная модель.
